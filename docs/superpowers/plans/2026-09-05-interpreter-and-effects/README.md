# Interpreter and Effects Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build, in `server/game/` only, the rules engine's resolution half: the pinned `Properties` set loaded from the eight tables (and the seeding step that puts authored content into them), the roll primitive over a seeded RNG that is game state, the effect grammar's two passes, the resolution stack interpreter (frames rebuilt from the log; steps that complete, ask, push or open a window; confirm gates; the simultaneous token spend), the one `IRulesEngine` implementation shared with the scheduler plan, and Grimdark Future's sequences — the four actions, shooting and melee over the shared attack-sequence → resolve-hits → deal-wounds, casting, morale, dangerous terrain, and containment (embarking and disembarking as part of a move, and a destroyed container disgorging what it held) — each tested headlessly against the rulebook.

**Architecture:** `Properties` is typed C# (`PropertySet`) built from rows; a `PropertySetDocument` is the authored JSON form, content-addressed by a canonical hash and seeded as rows once. The interpreter is generic: it reads the top frame's position and the log since that frame's last completed step (its *history*), runs the `IStep` the ruleset supplies, and turns the outcome into payloads — `step_completed`, `ask_opened`, `sequence_started`, `sequence_finished`. It never appends; `RulesEngine.Advance` returns payloads and the session appends them. Dice are a counter-based generator: the seed is the game's own stored seed, `GameInfo.RngSeed`, written once when the game is created and never changed, and the cursor is the number of dice drawn in the effective log, so replay and undo reproduce the same dice without storing any RNG state. `GrimdarkFutureRules` supplies sequences, steps, roll conventions, threshold functions, hooks and name checks; nothing under `Interpreter/`, `Effects/`, `Dice/` or `Engine/` names an OPR rule.

**Tech Stack:** .NET 10 (`net10.0`, C# 12), Npgsql 10.0.3 (the skeleton's), xUnit 2.9.3; `Tabletop.Geometry` (geometry plan), `Tabletop.Protocol` and `Tabletop.Content` (contracts plan); the game server skeleton's `IGameRules`, `IRulesEngine`, `GameState`, `CommandDispatcher`, `InMemoryEventLog`, `PostgresFixture`.

**Spec:** `docs/superpowers/specs/2026-09-03-action-sequences-design.md` (primary); `2026-08-28-resolution-design.md`; `2026-08-29-effect-grammar-design.md`; `2026-09-04-spell-effects-design.md`; `2026-08-29-content-values-design.md`; `2026-08-29-identity-and-enumerations-design.md`; `2026-08-28-game-flow-design.md`; `2026-09-04-scheduler-design.md` (the seam only); `2026-09-04-whole-design-review.md` (newest, wins); `docs/schema.md` (the eight `Properties` tables, the roll row); `docs/architecture.md` → Command / Event spine, Undo, Abilities, Rules as data. Rulebook: Grimdark Future v3.5.1 pages 7, 8–10, 11, 13–14, 20, 29–34, read for this plan. Earlier plans obeyed verbatim: `docs/superpowers/plans/2026-09-05-contracts-and-local-dev.md`, `2026-09-05-game-server-skeleton.md` (its *Interfaces needed → Scheduler and interpreter plans* is binding), `2026-09-05-management-api/README.md` (`GET /v1/properties`, the `properties` rows), `2026-09-05-geometry.md` (`Distance`, `LineOfSight`, `Cover`, `Movement`, `Bodies`, `Containment`, `Settling`).

## Global Constraints

- `net10.0`, `LangVersion 12`, `Nullable enable`, `ImplicitUsings enable`, root namespace `Tabletop.GameServer`; `obj/` under `obj/$(OS)/`; SDK `10.0.400`.
- Everything here lives in `server/game/`. Nothing is added to `libs/`; no rules type reaches `client/` (`architecture.md` → What is actually shared; CLAUDE.md).
- The skeleton's seam is extended, never replaced: members are added to `IGameRules` and implemented on `GrimdarkFutureRules`; `IRulesEngine`, `GameState`, `EngineResult`, `CommandDispatcher` keep their signatures; the one addition to `GameState` is the RNG seed (skeleton → Interfaces needed 2).
- One `IRulesEngine` implementation, `Engine.RulesEngine`, registered by `RulesEngineFactory` in place of `InertEngineFactory`. The scheduler plan plugs in through `Engine.IScheduler` (Task 10) and does not implement `IRulesEngine` itself. The one `IGameRules` is the skeleton's file; this plan adds its members (Task 8) beside the scheduler plan's — the merged interface is written in full in the skeleton plan → Interfaces → Produces → `Tabletop.GameServer.Rules`.
- The engine returns payloads and never appends or broadcasts. The interpreter never emits `ask_answered` or `ask_closed` (the dispatcher does; the scheduler emits one `ask_closed` with no answers for an unframed Ask of its own superseded by a menu edit) and reads `ask_closed` from the log to resume. It reads `state.Projection` and the effective log on every call and holds no state of its own between calls (scheduler → Nothing is an invariant; skeleton Task 6).
- Replay applies recorded results and never re-computes: a roll's threshold, modifiers and per-die raw and modified values are in the `RollRecord`; a step's settled parameters are in `StepCompleted.Values` (Interfaces needed 1). Nothing in a step's history is re-derived from `GameRules` (action sequences → The resolution stack).
- A step holds no C# locals across a suspension: every `IStep.Run` reads its position, values and history from the log and returns one outcome (action sequences → Why a stack and not a call stack).
- Only OPR's `GameRules` is built; 40k constrains interfaces (action sequences → What the interface must not assume). Nothing under `Interpreter/`, `Effects/`, `Dice/`, `Engine/` or `Properties/` may name a stat, roll, action, condition or catalog entry; Task 18 tests it.
- Enumeration, not validation: every Ask carries a server-computed legal set; legality of an answer is the dispatcher's (`LegalSetMembership` + `EnforcementPolicy`). The engine judges only its own commands (`RerollDice`, `SetDice`, `AddModifier`).
- Identifiers are `Guid.CreateVersion7()`; one world unit = one inch; geometry constants (1", 2"/4", 3", 6", 9", 12", 18") come from `GrimdarkFutureRules`, never from a library (geometry plan → Interfaces needed).
- Local only; Postgres from `docker-compose.yml`; the store tests use `[Collection("Postgres")]` and the skeleton's `PostgresFixture`. No hosting.
- Test-driven: every task starts with a failing xUnit test against an in-memory log and in-memory `Properties`; every OPR sequence has a test from the rulebook's worked example or a constructed one with scripted dice.
- Commit after every task, one-line imperative message, with the `Co-Authored-By` trailer naming the model.

**How the scheduler's turn Ask goes through this machinery** (the scheduler plan's Tasks 3–5 are written against this). The scheduler emits `AskOpened(new Ask(id, AskQuestions.Activate, prompt, [team], Options(unit × action), AllowPass: true, Sealed: false, WindowKind: null, FrameId: null))` from `IScheduler.Advance`; the dispatcher (skeleton Task 6) logs `ask_answered`/`ask_closed`; the scheduler returns `[]` while it is open; on the next call it reads the `ask_closed` from the effective log, emits its own `ActionRecorded(unit, action)` and, when `rules.ActionSequence(action)` is non-null, `starter.Start(state, sequence, new SequenceContext(unit, [], [], action))`; the interpreter then owns `Advance` until `sequence_finished` for that frame; the scheduler sees it, starts `rules.EndOfTurnSequences(state, properties, turn)` the same way, and when those have finished emits `turn_ended` with `rules.OnTurnEnded(state, properties, turn)`'s changes. `round_started.Changes` = `rules.OnRoundStarted(state, properties, round)`. The roll-off is `starter.Start(state, sequence, new SequenceContext(null, [], [], null))` for the `sequence` in `FirstTeamDecision.RollOffNeeded` (`GfNames.RollOffSeq`), and its result is `Values["place_1"]..["place_n"]` (team ordinals, best first; `winner_ordinal` = `place_1`) on the `step_completed` named `order` (`GfNames.RollOffOrderStep`) — the scheduler's `RollOff.Order` reads them and writes `round_started.Order`. The roll-off does not finish in the batch that started it: a frame with no actor and no parent is confirm-gated at every boundary past position 0 whatever the wait setting, to every team, so the engine rests with the frame live until a team answers (ruling 8). `Windows.ReactionOrder(state, actorTeam, reactingTeams)` is the one reaction-ordering policy: `IGameRules.OrderReactions` (scheduler plan) overrides it when non-null.

## Rulings

1. **Who seeds `Properties`, and when.** The game server, at startup, from documents embedded in its build, idempotently by hash (Task 4). The two servers are one system with one database, so the seeder inserts these rows itself; there is no endpoint or CLI hop between the build that carries the documents and the tables that hold them.
2. **"One try per spell" is scoped to the activation.** `GrimdarkFutureRules.OneTryPerSpellScope = "activation"` and `TriedThisActivation` scans from the activation's `sequence_started`, so a caster that failed a spell this activation may try that same spell again in a later activation.
3. **A later weapon group's attacks are not recomputed after an earlier group's casualties.** Every weapon group's attack count is fixed when the action starts, so a group that fires after casualties rolls as if nobody had died: p.8's *"all weapons are fired simultaneously"* beats the order `fire-groups` pushes the groups in. `fire-groups` records `attacks_<i>` and one `attacks_<i>_q<n>` per Quality value for every assigned group on the `shooting` frame before it pushes the first, and `determine-attacks` reads its own group's counts off the pushing frame (Tasks 13 and 14). There is no `RecomputeAttacksPerGroup` switch: nothing branches on it, and a `false` would advertise a switch that does not exist. A melee push records no count and `determine-attacks` counts live there, which is what p.9 asks for: melee is sequenced by hand, `Counter` striking first and the defender striking back with what survives, so each push is already at the moment the rulebook fires it. `Impact`'s *−1 per defending model with `Counter`* is the same case — the `impact` step follows the `counter` step by the rulebook's own order. **`Blast`'s cap is settled at the same moment:** p.13 caps hits at *"as many hits as models in the target unit"* without saying when they are counted, and they are counted with the attack counts. `fire-groups` records `defender_models_<i>` beside `attacks_<i>`, `determine-attacks` carries it onto its own frame as `defender_models` through the same `GfAttack.Pushed(frame, prefix)` reader, and the live count survives only as that reader's fallback for a push that recorded nothing. A second rule reads the same number: p.14's *"until all other models have been killed"* decides whether a hero blocks on its own `Defense`, and `roll-to-block` reads it off the same key, so a second group does not find the hero alone that the first group left. **p.11's cover majority is settled at the same moment:** p.8's *"all weapons are fired simultaneously"* settles the timing as it settles the attack counts and the `Blast` cap, so killing models cannot push a unit out of cover part-way through one action. `fire-groups` records `in_cover_<i>` through `GfAttack.InCoverAgainst`, `determine-attacks` carries it down as `in_cover`, and `roll-to-block` reads it there. Positions do not change between groups, so only the count is at issue. **No live read of the target's size is in the shooting path**, and each of the three keys falls back to the live reading for a push that recorded nothing, which is every melee push and every spell's hits.
4. **Catalog kinds and aggregation for the core rules the specs do not fix** (Task 3), against 3.5.1. `Stealth` is `all` and `Tough` is `none` ([identity and enumerations](../specs/2026-08-29-identity-and-enumerations-design.md) → The Stealth case). `Fearless` and `Regeneration` are `all` because 3.5.1 says so outright: both read *"a unit where all models have this rule"*. `Fast`/`Slow`/`Flying`/`Strider`/`Immobile`/`Furious`/`Relentless` are `model` with `all`. **`Artillery` is `all`**: *"When enemy units shoot at this model from over 9\" away, they get -2 to hit rolls"* is model grain while the hit roll is pooled per weapon group, and no hit belongs to a target model until the defender removes casualties after blocking (p.8). `Stealth` decides it, being the same to-hit penalty at the same range band and saying *"all models"*; cover's *"majority of models"* and `any` are the alternatives not taken. `Impact`/`Caster`/`Hero`/`Fear`/`Transport` are `none`; `Aircraft`/`Ambush`/`Scout` are `unit`. Army Forge lists most of these as unit rules; the management plan's import puts a name on every slot when the catalog says `model`, so the choice only changes where the import writes them, not what the engine reads. **The three `unit`-kind readings carry a consequence**: a `unit`-kind name on a model slot is read as the unit's rule, so a single joined hero with `Ambush` sets the whole squad aside. Ruling 13 states that cost against the alternative.
5. **The generic `Effects/` may know the two weapon stat names**, while OPR is the only ruleset ([closing the open questions](../specs/2026-09-09-open-questions-design.md)). `StatReader` reads `Range` and `Attacks` because `StatKind.Distance`/`Count` need a *which* (Task 7; Task 18 whitelists them). A second ruleset with differently named weapon stats gives `IGameRules` `StatRef RangeStat` and `StatRef AttacksStat`, and `StatReader` takes them.
6. **One sealed `TokenSpend` legal set serves every team.** `TokenSpend` is a cap per model (ruling 14), so there is no per-team maximum to place in the Ask, no clamp to derive one, and nothing of another team's total to leak. One Ask serves every team, since a sealed Ask closes when its addressed teams have all answered and one Ask per team would reveal the first answer to the last. There is no `Windows.MaxFor` and no `Values["tokens_max_<team>"]`.
7. **`Takedown`'s target is picked per model.** 3.5.1 p.14 reads *"This model may pick"*, so `GfGroups.Of` splits a takedown weapon type into one group per model, each holding that model's weapon, and each gets its own `pick-target-model`, its own pooled `roll-to-hit` and its own `deal-wounds`. `attack-sequence`'s `pick-target-model` is a `PieceSelection(Lookup.AliveModels(target), 1, 1)` to the attacker's team, after `determine-attacks` and before `roll-to-hit` (Task 13), and `deal-wounds` assigns every wound of that group to the named model without opening its allocation (Task 12). `Takedown` carries no *"Shoots at Quality 2+"*, so a takedown weapon hits at the model's own Quality unless its profile carries `Reliable`, and the catalog entry has no effects at all. One part of the sentence is not modelled: *"resolved as if it was a unit of [1]"*, so cover, `Blast`'s cap and the defence roll still read the whole target unit, and only the wound is redirected.
8. **Confirm gates and the actor.** The roll-off's dice are gated like any other roll. The gate goes to the acting unit's team where there is one, and `SequenceInterpreter.Advance` also gates a frame with **no actor and no parent** at every boundary past position 0, whatever `WaitsBetweenSteps` says, with one unsealed `Confirm` Ask **addressed to every team** (Task 8's `GateTeams`). Every team is the addressee because the roll-off has no acting unit and its result fixes turn order for all of them, so no team has a better claim to release it; the Ask is unsealed, so the dispatcher closes it on the first answer rather than waiting on every team being present before the first round. A nested actorless frame — the terrain-wounds `deal-wounds` — is ungated, since its own `assign` Ask already suspends it and the target's team would be the obvious addressee there. Two consequences. `GfRolls.RollOffSequence` is **two** steps, `roll-off` then `order` (Task 11): `dice_edited` reaches back into a `RollRecord` and never rewrites a `step_completed`'s `Values`, so the ranking has to be derived after the gate or an edit would change nothing. And the roll-off spans batches, which the scheduler plan absorbs — Interfaces needed 4. **One residue:** a root frame *with* an actor and a single step, which is the end-of-turn `morale-test`, pops before any boundary can gate it, so that die is unreachable once the frame is gone. Gating a root frame's terminal boundary would close that too, at the price of a confirm after every morale test.
9. **A unit cannot embark into an enemy's transport.** p.21 says a solid building's occupants *"must be from the same army"* and a `Transport` carries its owner's units, so `ContainersInReach` lists friendly containers only. **A consequence:** p.15's clause about occupants targeting *"the Transport itself"* is not reachable. `ValidTargets` offers enemy units only and a unit's own container is friendly, so no Ask ever presents it, and no legal move puts a unit inside an enemy container either. `Battlefield.InsideReach` still implements p.15 as written — a fellow occupant, or the container model — because the predicate is the faithful half of the pair; the only way to reach that branch is a menu-written state.
10. **A caster inside a container may cast**, at what is in there with it: `GfHooks.ReactionsAt` reads `Lookup.AliveModels`, so the window opens, and `GfCasting.SpellTargets` goes through `Battlefield.InsideReach`. `SpendCapacity` is positional for every model but the caster's own — p.13's `Caster` needs *"line of sight of the caster's unit"* and p.15's `Transport` denies an occupant any — so no other model's tokens reach such a cast, and a model inside a container never spends on a cast outside. **The caster's own remaining tokens do still modify its own roll** (ruling 14): its model is admitted to `EligibleSpenders` without measurement, being a model of the caster's own unit, so a cast from inside resolves at 4+ shifted by whatever the caster spends on itself rather than at a flat 4+. Task 17 implements this, and it is the one exception to a test positional on both ends. One edge is open: `SpellTargets`' **model-grain** branch measures per model and an occupant has no position, so a model-grain spell cast inside a container finds nothing to hit. Closing it means the same containment branch a second time, which is not worth writing until a model-grain spell exists.
11. **The disembark radius is 6", measured edge to edge.** Edge to edge is [the table domain model](../specs/2026-08-27-table-domain-model-design.md)'s rule — *"Distance is edge to edge between base shapes, never centre to centre"* — and the 6 is p.15's `Transport` figure. A garrisonable building has no automated exit, so nothing else needs a radius. `GfNames.ExitWithin = 6` for every container, measured edge to edge from the container's base, so the region is its footprint grown by 6" rather than a circle about its centre. A big vehicle therefore disembarks further from its hull centre than a small one, which is what measuring from the hull means. Geometry's `Containment.BaseFullyWithin` implements exactly that, and it is the only place the number is applied.
12. **A survivor with nowhere legal to stand is destroyed.** p.15 says the survivors *"must be placed fully within 6" of the transport"* and does not cover the case where no legal placement exists inside that radius, so this is a ruling and not a reading of the text. Task 19: `PlaceSurvivorsStep` writes for such a model exactly what `assign` writes for a casualty — wounds at the model's capacity, the model to the shelf, and the wounds added to the unit's activation tally — instead of parking it on the shelf unwounded, and the frame reports `Values["destroyed"]`. The shelf holds casualties and reserves alike ([game flow](../specs/2026-08-28-game-flow-design.md) → The shelf: *why* a model is there is a condition), so what separates the two answers is the wound count and the tally, not the location: the removal counts for p.10's end-of-activation morale test.

    defines the test against *"the model's Quality value"*, and the Hero rule overrides `Defense` alone: *"must use the unit's
    Defense until all other models have been killed"*. The clause that settles it is the same rule's *"The hero may take morale
    tests on behalf of the unit"*, which changes nothing whatever if the hero already used the unit's Quality, so the rule
    presupposes the hero's own. `Content/grimdark-future-core.properties.json` declares `Quality` and `Defense` at `model` level
    as well as `unit` level, and the model-level `Quality` is read.
    **The mechanism.** `StatReader.TargetNumber` takes an optional model and resolves either level: a `StatLevel.Model` ref
    reads the named slot's text and falls back to the unit's where the slot declares none, and the `ReplaceStat`/`ModifyStat`
    scan matches on the stat's name at either level, so `Reliable`'s 2+ still replaces a hero's own 3+. `StepContext.Plan` has
    an optional `threshold`, which is how a value read off a model reaches a plan without putting a model on `RollSpec` and
    therefore on `IGameRules`. `GfRolls.HitQuality` names p.4's *"the model's Quality value"* per attacking model, returning 6
    for a fatigued melee because p.9 replaces the value rather than modifying it, which is what keeps a fatigued unit at one
    pool. `GfAttack.Attacks` sums a group's Attack values **per Quality value** rather than per unit, so `determine-attacks`
    writes `attacks` and one `attacks_q<n>` per value and `roll-to-hit` rolls one pooled `GfRolls.HitPlan` per key, ascending,
    summing `extra_hits` and the `granted_<entry>_<amount>` counts over every pool. `fire-groups` settles those counts before it
    pushes the first group, as `attacks_<i>_q<n>` beside `attacks_<i>`, because ruling 3 fixes them there. p.4's *"we recommend
    having dice of multiple colors ... and then roll them all at once"* is the tabletop procedure for the case this creates: the
    hero and the squad carrying one weapon type that `fire-groups` merged into a single group. `GfAttack.HitsFrom` sums every
    `hit` roll on the frame, so the hits total is the same whether the step rolled one pool or several.
    **The Hero clause's sunset is a model count, and it is the frozen one.** `GfRolls.DefensePlan` takes `defenderModels` and
    reads the surviving model's own slot `Defense` only when that count is one, which for any slot without one is the unit's
    value and therefore branches on no rule name. The count is `defender_models`, settled by `fire-groups` as
    `defender_models_<i>` and carried onto the `attack-sequence` frame by `determine-attacks`: p.8 fires a unit's weapons
    simultaneously, so a second group must not find the hero alone that the first group left it. It is one key, not a
    `blast_cap_<i>` beside it, because both readers count the same number: p.13's cap of *"as many hits as models in the target
    unit"* and p.14's *"until all other models have been killed"* count the same models at the same moment.
    **The morale clause is resolved as always-when-it-helps:** while a joined hero is alive the morale threshold is the better
    of the hero's Quality and the unit's, one `Min` in `GfRolls.MoralePlan` over the unit's value and every living `Hero`
    model's own, with no Ask, so ruling 8's residue is unaffected. p.14's *"even if the hero is the last model remaining, it
    takes morale tests as the unit"* is about the starting-size comparison that separates Shaken from Rout, not about the
    threshold, which `GfHooks.AtHalfOrLess` keeps.
    **The readers of a hit roll.** `StepRecord.Rolls` is a list and `RollRecord` carries its own `Threshold`, so a step with two
    hit pools needs no wire change. Three readers handle more than one roll per step: the client's log panel offers its dice
    buttons per `RollRecord` and its `Animator` reads out every roll (client plan, Task 9 and Task 11); `Sim.Recording.LogLines.Dice`
    and the viewer's port of it print each roll with its threshold — `hit 3+ …; hit 5+ …` — so two hit pools in one step are
    distinguishable in a recording's `line`; the viewer's `RollPanel` iterates the list and shows each threshold.
    **A `unit`-kind entry on a model slot: the unit has the rule.** `Aircraft`, `Ambush` and `Scout` are the only `unit`-kind
    entries in the core set, and every rule a joined hero carries lands on its slot whatever its kind, so the case is routine
    and not only the corner a rule with `count < size` reaches. `Lookup.UnitHas` and `LiveProperties.Gather` both read such an
    entry off the unit's definition, holder-less, so the name lookup and the effect pass agree. **The cost is that one model
    grants the whole unit a unit-scoped rule**: a captain with `Ambush` sets a ten-model squad aside, and `Aircraft` on one slot
    gives every unit shooting at it -12" to range. **The alternative, answering false in both**, costs the opposite: a joined
    hero's own `Ambush` and `Scout` do nothing at all, with no diagnostic anywhere. Reading it off the definition rather than
    the living models is deliberate too: a unit-scoped rule does not stop being the unit's when the model carrying it dies, and
    `Ambush` and `Scout` are read before any model has a position.
14. **The player chooses which eligible model pays a team's token spend.** `TokenSpend` is a cap per model and `TokensSpent` a count per model, so a team distributes its spend across its own eligible models and the step deducts each named model's own count (Task 9, Task 17). There is no nearest-first payer selection, so no spend takes the tokens a player was holding for that model's own spell — every token holder is a `Caster(X)` model. `EligibleSpenders` is the one predicate, supplying the caps as well as the eligibility, and it includes the caster's own model: p.13 does not exclude it, it is admitted without measurement as a model of the caster's own unit, and its cap is what the spell's cost left it, because the caps are built in `spend-tokens`, after `pick-spell` deducted the cost.
