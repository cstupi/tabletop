# Rules suite

Design session, 2026-10-09. An end-to-end test suite, run by the simulator, that plays whole games exercising every
rule of the current Grimdark Future rule set and every spell, checks that each one fires and, for the core rules,
that it gives the right result, and reports coverage. A person can run it from the command line or from the viewer
and watch any game it played.

## The owner's requirements

- Coverage at depth C: every rule and spell is shown to fire; the core rules (pp.4–12), the 33 core special rules and
  one spell per effect kind are checked for exact results.
- Games, not one test per rule: each game exercises a few rules together, so a person can watch it play out and
  interactions get exercised.
- A run cleans up after itself and shows its results. A flag keeps the games. A run can be limited to chosen games.
- The games are worth going through: kept games open in the viewer and the client.
- In-process by default; the socket driver on a flag.
- A viewer page to choose games, run them and see the results (phase 2).

## Test games

A **test game** is a sim scenario with a theme, built by `ScenarioBuilder`, that additionally declares:

- **Covers:** the catalog names (rules and spells) it exercises.
- **Armies from catalog entries:** units are composed in the scenario from stats, weapons and catalog property names,
  not imported lists, so each unit carries exactly the rules under test. Spell casters carry `Caster(X)` and the army
  book uid their spells come from (`ModelSlot.ArmyBook`, p.13).
- **Script:** placements and answers that bring the covered rules into play (which unit activates, which action,
  which target, which spell, which casualties). Anything unscripted falls back to the sim's answer policy, so every
  game runs to its end.
- **Checks** (below).

A game is ordinary sim content: it plays on both drivers, writes a recording, and passes the sim's invariants.

### Groups

| Group | Covers | Shape |
| --- | --- | --- |
| `core` | pp.4–12: the four actions, moving, terrain (p.11–12), shooting, melee, morale, Shaken/Fatigued, deployment with Scout and Ambush, transports, objectives, the round-4 end under each enforcement setting | about 10 games |
| `special` | the 33 core special rules (`grimdark-future-core.properties.json`), three to five a game, chosen to collide (Furious against Counter, Fear in melee, Indirect against cover, Regeneration against Bane, Takedown, Limited, Aircraft's restrictions) | about 10 games |
| `army:<book>` | the hand-authored army-book rules (`grimdark-future-army-rules.part.json`) and the Aura, Buff, Mark and Debuff pattern games, grouped by the book that prints them | one or more per book that has catalog rules |
| `spells:<book>` | every spell of the book (190 distinct spells across 48 books): casters of that faction cast through the book's spells over the rounds, at friendly and enemy targets as each spell's targeting allows | one or more per book |

### Coverage

The suite holds the list of every catalog entry and every spell in the pinned property set. A run reports, for each,
the games that cover it and whether it fired in each. An entry no selected game covers is **uncovered**; a full run
(no `--only`) fails when any entry is uncovered. A text-only entry (`played: false`, generated by `scripts/ArmyBooks`)
is listed as not automated, with the count and the names, and is never counted or failed. A generated wrapper (an
Aura, Buff or Mark the generator wrote from its template) is covered by pattern: by the games whose `Pattern` is its
name's last word, when they passed and its base is covered and fired. Every hand-authored entry keeps its own game.

## Checks

Each game runs these, all of which must pass:

1. **The game ends** (`Outcome` ended or the scenario's declared round cap) and the sim's eight invariants hold.
2. **It fired**, for every covered entry: the log holds evidence attributable to that entry (*Attribution*).
3. **Exact results**, in `core` and `special` games and in one spell per effect kind: at chosen points the script
   fixes the dice of a roll with `SetDice` (an existing command, applied under every enforcement setting), and the
   check asserts the outcome the rule text states for those dice — hits, wounds, casualties, a modifier's size, a
   test's pass or fail. The expected value is written in the check from the rule text and quoted with its page; the
   sim never computes it with a second implementation of the rules.
4. **Scenario expectations**, as sim scenarios have today (`EventOfKind`, `Won`, `Warnings`, …).

### Attribution

`RollModifier.Source` already names the entry behind a roll modifier. Other effects (extra hits, a multiplied
wound, a re-roll, a granted property, a movement change, a hook-implemented rule) leave no name in the log. The
server adds one:

```csharp
// Events.cs — StepCompleted gains the entries that acted in the step, in order of application; null in older logs.
public sealed record StepCompleted(Guid FrameId, string Step, AskAnswer? Answer, IReadOnlyList<RollRecord> Rolls,
    IReadOnlyList<StateChange> Changes, IReadOnlyList<string>? Applied = null) : EventPayload;
```

`Applied` lists each catalog entry (property or spell) whose effect rows or ruleset hook changed the step's result.
The effects layer records an entry when one of its effects applies; a `Rules/GrimdarkFuture/` hook records the rule
it names. A cast spell names itself. "It fired" for an entry is: its name in some `Applied` or `RollModifier.Source`
of the game's effective log.

## Running

```bash
dotnet run --project sim -- suite                              # every game, in-process, nothing kept
dotnet run --project sim -- suite --only core,spells:<uid>     # chosen groups or game names
dotnet run --project sim -- suite --driver socket              # over the real servers (stack up)
dotnet run --project sim -- suite --keep                       # keep the games
dotnet run --project sim -- suite --list                       # games and what each covers
```

- **In-process** (default) writes nothing unless `--keep`, which writes each game's recording to `--out`.
- **Socket** seeds each game's rows, plays it over the game server and deletes the rows when the game finishes, pass
  or fail (`SocketRowSeeder.DeleteAsync`, `DeleteAccountsAsync`). Every game a run seeds carries the run id in its
  name; a run first sweeps games left by an interrupted run. With `--keep` the rows stay, so the game opens in the
  client and the viewer's live feed, and the recording is written.
- **Report:** a table per game (pass/fail, failed checks with their reason, seed, the command that replays that game
  alone with `--keep`) and per entry (covering games, fired, exact checks), then totals. The same data goes to
  `suite.json` in `--out`. Exit 0 only when every selected game passes and, on a full run, coverage is complete.
- The existing scenario catalog and `dotnet run --project sim -- <scenario>` stay as they are; the suite is beside
  them.

## The viewer's Tests page (phase 2)

- **Runner service:** a dev-only HTTP service in compose (`sim-runner`, `127.0.0.1:5180`) hosting the same suite
  code: `GET /suite` lists games and coverage; `POST /runs` starts a run (selection, driver, keep) and returns its
  id; `GET /runs/{id}/events` streams each game's result as it finishes (server-sent events); `GET
  /runs/{id}/recordings/{game}` serves a kept recording. One run at a time.
- **Tests page** in the viewer: games grouped as above with what each covers; select, Keep toggle, driver choice,
  Run; results arrive live; the coverage table; per finished game **Watch** (opens its recording in the viewer) and,
  for kept socket games, **Open live** (the viewer's spectator feed on that game).

## Out of scope

Authoring the army-book rules still text-only (army-book rules spec, *Authored rules*): the suite lists them as not
automated and covers what the catalog plays. Rules engine fixes the suite finds are separate work, each
recorded where the suite reports it.
