# server/game

`Tabletop.GameServer` (`net10.0`, ASP.NET Core): the WebSocket game server. Clients, `sim/` and `viewer/` connect to `/ws`.
It reads management's rows, owns each game's append-only event log, and hosts the rules engine.

## Layout

- `Program.cs`: DI, `PropertiesSeeder` at startup (not in the `Test` environment), `/ws`, listens on :5200.
- `Auth/SessionVerification.cs`: `ISessionVerifier`, `StytchJwtVerifier`, `HttpJwksSource` (JWKS cached 10 minutes).
- `Configuration/`: `GameServerOptions` (from `TABLETOP_*`), `DotEnv`.
- `Session/`: `ConnectionHandshake`, `SessionRegistry`, `Hydrator`, `GameSession` (partials Connect, Lobby, Setup, EndSetup, Frames, Facts), `SocketConnection`, `PresenceTable`, `SessionHost`.
- `Dispatch/`: `CommandDispatcher`, `EnforcementPolicy` (silent/warn/strict), `HandMoves` (the `hand_move` breach), `LegalSetMembership`, `MenuTranslation`, `EventFilter`.
- `Log/`: `IEventLog`, `PostgresEventLog`, `InMemoryEventLog`, `Replay`.
- `Persistence/`: `IGameRows`, `PostgresGameRows` (+ `.Writes.cs`), `RowMapping`.
- `Setup/DraftEditor.cs`: edits to the setup draft.
- `Rules/`: `IRulesEngine` and `GameState`, `IGameRules`, `InertEngine`.
- `Rules/GrimdarkFuture/`: `GrimdarkFutureRules` and its `Gf*` partials (sequences, rolls, hooks, names).
- `Engine/`: `RulesEngine`, `RulesEngineFactory`, `GameOverAsk`, `IScheduler`/`ISchedulerFactory`.
- `Properties/`: `PropertySet` (pinned set), `PropertySetDocument`, `IPropertiesStore`, `PostgresPropertiesStore`, `PropertiesSeeder`.
- `Content/`: `grimdark-future-core.properties.json`, `grimdark-future-army-rules.part.json` (hand-authored), `grimdark-future-army-book-rules.part.json` (generated by `scripts/ArmyBooks`), `army-books/<uid>.book.json`. All embedded resources.
- `Dice/`: `DiceSource`, `ScriptedDice` (tests), `DiceCursor`, `Roller`, `RollPlan`.
- `Effects/`: `LiveProperties`, `RollEffects`, `Conditions`, `StatReader`, `Lookup`, `Interaction`, `AppliedEntries`.
- `Interpreter/`: `SequenceInterpreter`, `FrameReader`, `Steps`, `StepContext`, `Windows`, `Battlefield`, `Sight`.
- `Scheduler/`: `SchedulerFactory`, `AlternatingActivationScheduler`, `PlayerTurnScheduler`, `SchedulerBase`, `RollOff`, `TurnCycle`, `ActivationOption.cs`, `SchedulerTypes.cs`.

## How it works

- A threshold read from a stat carries its basis: `StatReader.TargetNumber` returns a `TargetRead` (value, printed value, each replace_stat and modify_stat row), `StepContext.Plan` puts its `ThresholdBasis` on the `RollPlan` and `Roller` on the `RollRecord`. `StatReader.Peek` reads without spending or recording, for a hit pool's basis in `roll-to-hit`. Casting's 4+, fatigue and a property's own roll carry none.
- What the combat log reads off a roll (combat-log spec → What the server adds): `RollEffects.Attributed` sets `RollModifier.Via` from `LiveSet.GrantorOf` (pass one's `GrantedBy`, or the per-die grantor `LiveSet.WithGranted` stamps as `LiveProperty.Via`); `roll-to-hit`, a spell's `hit` and `roll-to-block` (the defender's side) pass `RollEffects.Triggers` (pure; `attacks: false` on the dice extra attacks added, which add none of their own) to `StepContext.Roll`, which stamps `Die.Triggered` on the record's dice and a forced reroll's; `GfRolls.Cover` counts p.11's majority, `GfAttack.CoverOf` turns it into a `CoverVerdict` (Indirect's dropped sight half as `IgnoredBy`), `fire-groups`/`determine-attacks` settle it as `in_cover`, `cover_models`, `cover_of`, `cover_indirect`, and `roll-to-block` hands the one verdict to every group's `GfRolls.DefensePlan`, which names a cover suppressor (`LiveSet.Suppressors`) as `IgnoredBy`; `RollPlan.Cover` reaches `RollRecord.Cover` through `Roller`. Melee and spell hits carry none.
- `/ws` accepts a socket; `ConnectionHandshake` reads the first frame, which must be `Connect`.
- Handshake order: client version against `MinimumClientVersion` (`Rejected(UpgradeRequired)`), `ISessionVerifier` (`Rejected(InvalidSession)`), `IGameRows.FindParticipantAsync` (`Rejected(NotAParticipant)` unless the session is an admin and the game exists), `SessionRegistry.GetOrHydrateAsync`, `GameSession.ConnectAsync` (`WatchAsync` for an admin watcher), then the read loop.
- An admin watcher (session `roles` claim holds `admin`, no participant row) gets what a teamless participant gets, with `Welcome.ParticipantId` `Guid.Empty`. `GameSession` holds watchers in `_watchers`, apart from `_clients`, so lobby, presence and Asks never meet one. A watcher's sight query is answered; its command, edit, presence or ping is `Refused` with `RefusalReason.Watcher` and nothing else.
- A verifier or database exception closes the socket 1011; it is not a rejection.
- `StytchJwtVerifier` checks RS256 against Stytch's JWKS, issuer `stytch.com/{project}`, audience the project id, and the top-level `account_id` claim (our account UUID). The `roles` claim (Stytch role ids) becomes `VerifiedSession.Roles`; absent is none. An unknown `kid` refetches the keys.
- `Hydrator` builds a `GameSession` from the rows, the `game.game_event` log and `GameRulesRegistry.Resolve(info.GameRules)`. The engine comes from `IRulesEngineFactory.Create(rules, info)`.
- `GameSession` is one game in memory. All mutation runs on its mailbox loop (a `Channel`), so there is no lock. A newer socket for a participant replaces the older.
- A command frame goes to `CommandDispatcher.Dispatch`, which returns `Applied(events, warning)` or `Refused`. It never appends or broadcasts.
- `Classify` sorts commands: `Override` (menu edits: moves, markers, wounds, conditions, score, round), `Undo`, `Abandon`, `Answer`, `Engine` (dice commands).
- `GameSession.RunToRestAsync` is the write path for a command, the catch-up at start and the end of setup: the command's events, then `IRulesEngine.Advance` repeatedly until it returns nothing (cap 10000 iterations), each batch applied to the projection as it comes; then one `IEventLog.AppendAsync` of every batch (one transaction, one `NpgsqlBatch`), then each batch broadcast as its own `EventsMessage`, in order. Nothing is sent before the append returns.
- A failed append faults the session before anything is sent; the projection, ahead of the log, is discarded with it. An `Advance` exception or a `ProjectionDesyncException` appends what was staged, then faults.
- A fault closes every socket 1011.
- `RulesEngine.Advance` is `SequenceInterpreter.Advance` while frames are on the stack; the `IScheduler` runs only when no framed Ask is open and the stack is empty.
- A `GameEndingBreach` from `IGameRules.JudgeAdvance` (Grimdark Future: `mission_length`, round 5 about to start) ends the game under `strict`, passes quietly under `silent`, and under `warn` is `OfferEnd`: `GameOverAsk` opens one sealed, unframed `game_over` Ask (End, Continue) to every team with a participant, once per round boundary. Any End closes it at once (`GameOverAsk.Settle`) and the next `Advance` writes the `strict` `game_ended`; every team's Continue lets `round_started` through with the warning. A `set_round` while it is open closes it unanswered.
- Undo is `Undone(toSeq)`: events are never removed. `EventApplier.EffectiveLog` is the live log; `Replay.To` rebuilds a projection to a seq.
- Hydration decides from the log, not the row: an ended log over a `playing` row writes the row and advances nothing; any other log catches up through `RunToRestAsync`.
- Rows written: in `lobby` and `setup`, teams, participant team/army, configuration, `StartSetupAsync` (draft tree, status to `setup`), `WriteDraftAsync` (one write per drop), `EndSetupAsync` (final tree, `army_snapshot` per participant, status to `playing`).
- From `playing` on, the only row write is `EndGameAsync` (`playing` to `ended`, guarded on `playing`), after the log ends the game. A failed write is logged and the next hydration retries it.
- The engine holds no state between calls. A step reads position, values and history from the log (`FrameReader`) and returns one outcome: `Complete`, `Finish`, `OpenAsks`, or `Push`.
- `RulesEngineFactory` loads the game's pinned `PropertySet` by `game.PropertiesHash` (cached per hash) and calls `ISchedulerFactory`. A missing hash throws `PropertiesNotFoundException`.
- `SchedulerFactory` picks `AlternatingActivationScheduler` or `PlayerTurnScheduler` from `game.SchedulerShape`.
- Dice: die `i` of a game is a pure function of (`rng_seed`, `i`) in `DiceSource.Draw`. `DiceCursor.DrawnSoFar` counts every die in the whole log, undone events included (roll records plus rerolls); edits draw nothing.
- Effects run two passes over live properties. Pass one (`LiveProperties`, to a fixed point): which properties are live, grants, suppressions, parameter changes, suppressed modifier classes. Pass two (`RollEffects` and readers): what the live properties do to a roll or stat.
- `StepCompleted.Applied` lists the catalog entries that acted in that run of the step, each once, in order of first application;
  null when none did. Each `StepContext` owns an `AppliedEntries`: a live set settled through `StepContext.Settle` records every
  effect row that applies, and a ruleset hook that changes a result adds the rule it names (`ctx.Applied.Add`). A rule that acts in
  the scheduler or in action legality (Scout, Ambush, Immobile) completes no step and is not listed; Aircraft's action restriction is
  not listed either, but its move (p.13: +30", no terrain) is, on the move step. The rules suite reads it
  to judge which rules fired.
- `SequenceInterpreter` opens a "Continue: {step}" confirm Ask between steps when `Info.WaitsBetweenSteps` is on, gated to the actor's team. The client never offers the flag; it serves development. A frame with no actor and no parent (the roll-off) is always gated, to every team.
- A `MoveModels` goes through `HandMoves.Judge` and `EnforcementPolicy.Decide`: placing the unit the actor's team last picked at a deploy Ask from the shelf onto the table, or inside a container the rules allow (`IGameRules.MayDeployInside`), is legal; anything else is `hand_move`, which `silent` accepts, `warn` warns and `strict` refuses. A placement on another model's base is
  `IGameRules.PlacementBreach`'s (Grimdark Future: `move_overlap`, `GfMoves.OverlapBreach`), legal or not; it is appended to a `hand_move` breach's detail.
- An Ask answer inside its legal set is also asked of `IGameRules.AnswerBreach`, which names the rule broken; the dispatcher decides it as a
  `Breach` (`StrictRefuses(Illegal)`) under the enforcement setting. Grimdark Future's (`GfRules.Moves.cs`) are `move_not_offered`, `move_exit`,
  `move_off_table`, `move_impassable`, `move_allowance` (`GfMoves.PathBreach`, p.7 and p.11, against the Ask's own parameters, plus the landing
  against every impassable volume, which a Flying unit's Ask does not list, unless the region `IgnoresTerrain`: an Aircraft, p.13), `difficult_cap`
  (`GfMoves.DifficultCapBreach`: p.11 holds every model of a `MoveRegion` to its `DifficultCap` once any model's path, or an earlier segment of the
  move, enters difficult ground), `aircraft_minimum` (`GfMoves.MinimumBreach`: every model moves at least `MinDistance`, p.13) and p.7's contact clauses
  (`GfMoves.ContactBreach`: `move_overlap` on a base, `move_through_models` unless the region `PassesModels`, `move_separation` within the region's `Separation`). All read the
  answer through `GfAnswers.Moves`, the reading the move steps apply, so a check never passes a relocation the step reads differently.
- `SightQuery` is answered to the asker alone from `Sight.Line` per model pair and `IGameRules.Shooters`: nothing appended or broadcast, no `AtRest`. `ModelFacts` (`IGameRules.MaxWounds`) goes to a client on connect once playing, and to everyone after a batch that changes a value. `Shooters` reads the game's `PropertySet` through `IRulesEngine.Properties`; Grimdark Future's calls `GfAttack.AttackInteraction`'s frame-optional core with no frame, the core the fire groups share.
- `IStep.Label` puts a step in its sequence's outline; `SequenceStarted.Outline` carries the labelled steps in order.
- `Windows` offers interrupting reactions as one Ask per eligible team, in reaction order (`GameRules.OrderReactions`, else turn order after the actor's team).
- `Rules/GrimdarkFuture/` is the only place a rule is named. The interpreter, effects, dice and generic scheduler know no ruleset; the scheduler's Grimdark Future hooks are `GfRules.Scheduling.cs` and `GfRules.Deployment.cs`.
- An army-book Buff, Mark or Debuff is a pick entry: a `model` entry with `targeting` and `once` rows at `before-attacking`. `GfHooks.ReactionsAt` offers each carrying model's use (`GfPick`); `pick-rule` asks `rule_target` and writes one grant per row on the unit picked. A carried pick entry exposes no rows, and a granted row's `at_point` holds wherever it is read.
- `CatalogEntry.Played` is false only on a generated text-only entry; `LiveProperties.Gather` skips it as an absent name.

## Commands

```bash
docker compose up -d                                        # Postgres, MinIO, management :5100, game :5200
dotnet run --project server/game/Tabletop.GameServer.csproj # host run; stop the container first: docker compose stop game
dotnet test tests/Tabletop.GameServer.Tests                 # unit; nothing running
dotnet test tests/Tabletop.GameServer.Tests --filter "FullyQualifiedName~GfAttack"
./scripts/army-books fetch                                  # downloads books from Army Forge (the only network call)
./scripts/army-books generate                               # rewrites Content/army-books/ and the army-book rules part from the fetched copy
```

- Under compose, `game` runs `dotnet watch run` over the bind-mounted repo with `TabletopBuildSlot=-game`, so it builds into `obj/Unix-game/` and `bin/-game/`. A host `dotnet build` never disturbs it.
- `game` starts after management is healthy, which has run the migrations.
- Both servers bind `127.0.0.1` under compose.
- `dotnet run` reads `.env` through `DotEnv` and needs `TABLETOP_DB_CONNECTION` and `TABLETOP_STYTCH_PROJECT_ID`.

## Conventions and pitfalls

- The engine never appends or broadcasts. The session does both.
- Dice are never drawn from a clock or a global generator. Anything random goes through `Roller` and `DiceCursor`.
- Authored properties are `Content/*.properties.json`, every `*.part.json`, and every `army-books/*.book.json` of the same game rules. `PropertiesSeeder.Compose` folds them into one document per core file, ordered by name and uid.
- Seeding is by content hash at startup. Editing any of these files makes a new set with a new hash; games already created keep their hash. Stored rows keep the document's order in `position` (actions, effects, conditions, condition values); a present set with null positions gets them from its document, ids kept.
- Two sources carrying an entry of the same name must have equal canonical forms, else `Compose` throws.
- A `*.book.json` is never edited by hand. Fix `scripts/ArmyBooks` and run `./scripts/army-books generate`.
- `grimdark-future-army-book-rules.part.json` is never edited by hand. Authoring a name in the hand part needs `./scripts/army-books generate` before the server composes, or `Compose` refuses two entries of one name.
- New content files need the `EmbeddedResource` globs in `Tabletop.GameServer.csproj`; the three patterns there are `*.properties.json`, `*.part.json`, `army-books/*.book.json`.
- The game server writes a game's rows only in `lobby` or `setup`, plus `playing` to `ended` once. Management writes at creation, end, leave and delete.
- `WaitsBetweenSteps` is the per-game flag behind every "Continue" Ask (`SequenceInterpreter.cs`). Players never see it.
- Every `IGameRules` wrapper that forwards by hand (the tests' `WithSequences`) forwards `MaxWounds`, `Shooters`, `MayDeployInside`, `AnswerBreach` and `PlacementBreach`, or a wrapped ruleset answers 1, nobody, never and nothing broken.
- `ProjectionDesyncException` at hydration is a server bug: every reconnect replays the same event.
- The first `Connect` frame has `HandshakeTimeout` (10 s by default).
- Schema changes are management migrations, never made here.

## Tests

- `tests/Tabletop.GameServer.Tests`, xUnit. The unit suite runs over `InMemorySeeder` (`InMemoryGameRows`, `InMemoryEventLog`, `InMemoryPropertiesStore`); `GameServerFactory` serves a seeder's stores and `TestKeys`' JWKS, so nothing reaches Postgres or Stytch.
- E2E (`--settings tests/e2e.runsettings`): `PostgresGameRowsTests`, `PostgresEventLogTests`, `PropertiesStoreTests`, over `PostgresFixture` (`[Collection("Postgres")]`, `TABLETOP_DB_CONNECTION`, the Docker Postgres with management's schema).
- `Infrastructure/` holds the fixtures: `GameServerFactory`, `InMemorySeeder`, `InMemoryGameRows`, `PostgresFixture`, `SchedulerHarness`, `ScriptedStarter`, `FixedAskEngine`, `TestProperties`, `FakeRules`/`StubRules`, `RecordingClient`.
- `ScriptedDice` fixes faces. Rules tests are named `Gf*Tests.cs`.
- `EventLogContract.cs` and `GameRowsContract.cs` run against both the in-memory fake and the Postgres adapter.
